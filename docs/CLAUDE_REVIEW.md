Review based only on the specification and the summary you provided. I did not inspect the code, data, or manuscript.

1. **Simultaneous skills may leak the current attempt.** The spec says multiple skill observations are "averaged into one input vector and simultaneously predicted." If that input is built from attempt t's own outcomes, the model sees the labels it predicts. Build the input for attempt t only from attempts strictly before t, and add a unit test that perturbs attempt t's labels and asserts unchanged predictions for attempt t.

2. **The 383 user/log_id ties need an explicit ordering rule.** Same-timestamp groups are atomic, but tied rows that differ in timestamp, or that share a log_id across learners, are not covered. Key groups on (learner, log_id) and state the tie-breaker. The tie-breaker must not depend on the outcome column. Check this by shuffling rows within ties and confirming the splits, windows, and predictions are identical.

3. **Binarizing before splitting needs a sensitivity analysis.** The ≥1−1e−8 rule is a fixed label definition, so it is not itself leakage. But near-exact equality is brittle, and the choice drives every binary metric. Report results at a few thresholds (for example ≥0.99 and ≥0.9) and keep the continuous-score task separate, with regression-style metrics rather than Brier on the binarized label.

4. **Time is being ignored in a dataset named FORGET-SE.** If the benchmark is about forgetting, dropping time fields may remove its main signal. The spec's rule is that time is used only if chronology is trustworthy. So first verify that log_id order matches timestamp order within each learner, and report that check. If it fails, state plainly that forgetting effects are untestable on this data.

5. **"Readiness proxy" still implies mastery.** DKT and SAKT outputs are next-attempt success probabilities. They blend skill, exercise difficulty, fatigue, and rubric strictness. Use "predicted next-attempt success" in code, UI, and reports, and keep "readiness" only as an explicitly qualified label. Also report whether predictions track item difficulty.

6. **BKT parameters may not be identifiable here.** With about 58 records per learner and 186 learners, slip, guess, and learn rates are often poorly identified. Report the fitted parameters, flag degenerate fits (for example guess above 1−slip, or learn rate near zero), and constrain the fits. Do not present BKT mastery as an estimate of psychological state.

7. **The recommendation rule is internally inconsistent.** It ranks "fragile" skills by predicted success, but high predicted success means a skill is less fragile. Define fragility in one place, for example low predicted success combined with low evidence coverage, and write the rule as a formula. Also state that the logged policy is non-randomized, so recommendations cannot be validated offline and any feedback loop is unmeasured.

8. **Preprocessing and skill vocabulary must be fitted on training data only.** The spec says this about statistics, but evidence-coverage counts, skill-prior smoothing, skill vocabulary, and any exercise-level statistics could still use full-data counts. Put every such computation in the training fold, and add a check that the saved artifact's fitted statistics match a training-only refit.

9. **Learner-level splitting may still leak through shared identities.** Learner IDs may recur across sources, and exercise or item IDs may appear in both training and test. Confirm that pseudonymous IDs are unique across the whole pipeline, and report the number of exercise IDs that appear only in test. Missing outcomes also need a rule: they should not be imputed with 0 or with model predictions, because that feeds the model its own output as ground truth.

10. **Synthetic demo results are circular, and the statistics are thin.** Synthetic fixtures generated by the same taxonomy and rules the models learn will produce high scores that mean nothing. Include parameter recovery against the known generator, and add a misspecified generator (for example non-Markov forgetting) that the models should fail on. Keep demo metrics out of the UI's evidence panels, and label them as pipeline checks. For the real benchmark, with roughly 30 to 40 test learners, report paired learner-bootstrap differences against the baseline, not just point estimates. Claim a neural advantage only when that interval excludes zero, and handle undefined per-skill AUC when a class is absent.
